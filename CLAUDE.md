## Project

Seenzo — an AI Visibility Report landing page + lead-capture site for Indian businesses ("Get seen by AI"). Currently a marketing site (demo-only forms, no backend) plus a UI-only admin dashboard, all backed by mock data. Product of KlivIQ Technologies OPC Private Limited.

This project is connected to **Lovable** (lovable.dev) — commits pushed to the connected branch sync back to the Lovable editor. Avoid rewriting published git history (force push, rebase/amend/squash of already-pushed commits): it breaks history on Lovable's side and can lose the user's project history in the editor. Keep the branch in a working state since Lovable syncs from it directly.

## Architecture

**Stack:** TanStack Start v1 (file-based router + SSR) + React 19 + TypeScript (strict) + Tailwind CSS v4 + shadcn/ui (`new-york` style, Radix primitives) + Vite 8, built via `@lovable.dev/vite-tanstack-config`.

### Routing (`src/routes/`)

File-based routing per TanStack Start conventions — see `src/routes/README.md` for the full naming table (`$id` dynamic, `{-$category}` optional, `$` splat, `_layout` layout routes). Key rules:

- `src/routes/__root.tsx` is the only app shell — sets all `<head>` metadata (SEO/OG/Twitter/JSON-LD), wraps every page in `QueryClientProvider`, and renders the root `<Outlet />`. Do not remove that `<Outlet />`.
- `routeTree.gen.ts` is auto-generated by the TanStack router plugin — never hand-edit it.
- Do not introduce `src/pages/`, `_app/index.tsx`, or `app/layout.tsx` — those are Next.js/Remix conventions and don't apply here.
- Current routes: `/` (landing page, `index.tsx`), `/r/$slug` (mock AI-visibility scan report), `/admin` (internal dashboard, `noindex`, unauthenticated, not linked from public nav), `/privacy`, `/terms`.

### Server runtime (edge-compatible)

The build targets an edge/serverless runtime (Cloudflare Workers via Nitro). Server-side code must avoid Node-only APIs (`child_process`, `sharp`, `fs.watch`, dynamic filesystem access) — use Web-standard APIs and `fetch` instead.

- `src/start.ts` — `createStart` with a request middleware that catches server errors and renders a static error page instead of letting them bubble as raw 500s.
- `src/server.ts` — wraps the TanStack Start server entry (`@tanstack/react-start/server-entry`); also detects the case where h3 silently swallows an in-handler throw into a generic `{"unhandled":true,"message":"HTTPError"}` JSON 500 (try/catch alone doesn't catch this) and replaces it with the rendered error page, recovering the real error via `src/lib/error-capture.ts`'s out-of-band capture.
- `vite.config.ts` redirects TanStack Start's bundled server entry to `src/server.ts` for this reason. Don't add `tanstackStart`/`viteReact`/`tailwindcss`/`tsConfigPaths`/nitro plugins manually — `@lovable.dev/vite-tanstack-config` already wires all of that (see comment at top of the file).

### Error handling

Two independent layers, both funneling into `renderErrorPage()` (`src/lib/error-page.ts`, a plain inline-styled HTML string, not a React component — it must render without the app bundle):

1. Server-side: `src/start.ts` middleware + `src/server.ts` h3-swallow detection (above).
2. Client-side: `__root.tsx`'s `errorComponent`/`notFoundComponent` route options, which also report to Lovable's error tracking via `src/lib/lovable-error-reporting.ts` (`window.__lovableEvents.captureException`, a no-op if that global isn't present).

### UI components

- `src/components/ui/` — shadcn/ui primitives (generated, Radix-based). Treat as vendored; regenerate via shadcn CLI rather than hand-rewriting wholesale.
- `src/components/site/` — page-specific components: `Logo`, `ScanForm` (react-hook-form + Zod, see `src/lib/scan-schema.ts`), `SiteShell`.
- Path alias `@/*` → `src/*` (configured in `tsconfig.json`, `components.json`, and Vite).
- Styling: Tailwind v4 CSS-first config in `src/styles.css`. Two token systems coexist — brand marketing tokens (`--color-brand`, `--color-ink`, `--color-spark`, fonts) for the landing page, and shadcn semantic tokens (`--background`, `--primary`, etc., defined in oklch, light + `.dark` variants) for shadcn/ui components. When adding a new semantic color, add it to both `:root`/`.dark` and the `@theme inline` block (see comment in `styles.css`).
- `src/routes/admin.tsx` and `src/routes/r.$slug.tsx` intentionally use a separate dark slate/amber palette (not the shadcn tokens) to read as an internal tool / report artifact rather than the marketing site.

### Mock data / no backend yet

Nothing in this repo currently talks to a real backend. `ScanForm` validates client-side only; `/admin` (`src/lib/mock-admin.ts`) and `/r/$slug` use hardcoded mock data with local-state-only mutations (status changes, notes, CSV export, delete) — no network calls. `.lovable/plan.md` documents the intended `/admin` UI spec in detail if extending that dashboard. When wiring up real data, expect Lovable Cloud / Supabase per the README's environment-variables section.

### Linting

`eslint.config.js` bans importing the `server-only` npm package (not used by TanStack Start — rename modules to `*.server.ts` or use `@tanstack/react-start/server-only` instead). Prettier is run as an ESLint rule (`eslint-plugin-prettier`), so `bun run lint` and `bun run format` should agree; `no-unused-vars` is intentionally off.

## Backend Build Context (Seenzo — Active Build)

This repo is transitioning from mock-data-only to a fully working product. The backend must be built without breaking any existing UI. All existing routes, components, and styling are frozen — backend wiring only.

### What needs to be built (in this exact order)

1. Supabase client (typed, service role for server, anon for public)
2. Scan request server function — form submit handler
3. Email verification route — token validation + Inngest trigger
4. Inngest scan pipeline — 4 steps: fetch → checks → score → store
5. 30 checks + scoring engine (scoring/v1.json with weights)
6. Report page /r/$slug — replace mock data with live Supabase reads
7. Report delivery — Resend email + Meta WhatsApp Cloud API
8. Follow-up sequence — Inngest step.sleep Day 2/5/10
9. Admin dashboard — Supabase Auth + live data
10. Soft launch gate — seenzo.in scans itself ≥90

### Runtime constraint

Edge-compatible (Cloudflare Workers via Nitro). No Node-only APIs. No child_process, no sharp, no fs.watch. Use fetch and Web APIs only. Crawler runs inside Inngest steps (each step ≤30s). PDF = window.print() only.

### Package manager

Bun. Always use `bun add` not `npm install`.

### Database

Supabase Postgres, Mumbai region (ap-south-1). Schema already run. Tables: leads, scans, scan_checks, activity_log, url_cache.

### Services

- Email: Resend (sender: reports@seenzo.in)
- Background jobs: Inngest (durable functions, step.sleep for follow-up)
- Rate limiting: Upstash Redis
- WhatsApp: Meta WhatsApp Cloud API direct

### Scoring engine

Category weights: Crawlability 25% · Structured Data 20% · Metadata 15% · Content 15% · India Presence 15% · Trust 10%
Grades: A ≥85 · B 70–84 · C 55–69 · D 40–54 · F <40
Each check returns: pass | partial | fail + evidence string + fix_text + effort (low/med/high)
Store scoring_version: "v1" on every scan.

### Key business rules

- No report sent to unverified email — ever
- 1 scan per email per 30 days (serve cached report on duplicate)
- 3 scans per IP per day
- Honeypot field must be empty (bot detection)
- SPA detection is the hero finding — triggers special report verdict
- Lead heat score = 100 minus Seenzo Score + bonuses for business email, CTA clicks, report views
- Hot lead (heat ≥70) triggers immediate WhatsApp alert to +919840497937

- routeTree.gen.ts (auto-generated, never edit)
